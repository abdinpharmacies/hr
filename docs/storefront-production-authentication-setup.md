# Authentication setup for store.abdinpharmacies.com

Prepared 2026-11-17 from the current Callcenter gateway and ecommerce authentication addon source. This is a setup guide; no production settings, webhooks, services or credentials were changed, and no authentication messages were sent.

The current implementations use different transport paths:

| Channel | Authentication route | Configuration owner |
| --- | --- | --- |
| WhatsApp | Storefront queues challenge → Callcenter-hosted auth worker fetches it over HTTPS → Meta sends OTP → signed receipts return through the gateway | Storefront authentication transport plus Callcenter `auth.json` and existing WhatsApp sender configuration |
| Telegram | Storefront authentication addon → Telegram Bot API; Telegram sends bot updates to the storefront webhook | Storefront authentication settings and its authentication bot |

Telegram customer authentication currently does not pass through the Callcenter chatter gateway. The repository documents `Abdin_Pharmacy_Bot` for customer authentication and `abdin_callcenter_bot` for staff chatter; confirm these usernames against the tokens actually assigned. Give each bot exactly one update consumer. Routing both authentication channels through the Callcenter host would require an additional Telegram authentication relay; settings alone do not implement that relay.

## 1. Production storefront: common requirements

Use the actual Odoo database serving `https://store.abdinpharmacies.com`; the public domain does not determine the database name. Install `ab_ecommerce_storefront` and `ab_storefront_whatsapp_auth` on that database, with their declared dependencies. The optional `ab_ecommerce_api_whatsapp` addon is required only when using the optional customer API.

Use a valid HTTPS certificate, correct hostname-to-database routing, and trusted-proxy forwarding so Odoo sees HTTPS. Configure `proxy_mode = True` behind that trusted proxy. The worker must reach the final HTTPS origin directly; its client does not follow redirects. Preserve Authorization, X-Odoo-Database and provider signature/secret headers, and avoid request-body logging on authentication routes.

Keep the database's `database.secret` stable and protected: existing authentication hashes/encrypted queues depend on it. There is no shared customer password or OAuth client secret between the two Odoo servers for this transport.

Set the following storefront System Parameters or the corresponding Storefront Authentication settings:

| System Parameter | Production value |
| --- | --- |
| `ab_storefront_auth.base_url` | `https://store.abdinpharmacies.com` |
| `ab_storefront_auth.development` | `False` |
| `auth_signup.invitation_scope` | `b2c`, when public customer registration is wanted |
| `auth_signup.reset_password` | `True`, when password recovery is wanted |

## 2. Production storefront: WhatsApp authentication

Open **Settings → WhatsApp Authentication** and configure one transport for the production website:

| Field | Value |
| --- | --- |
| Website / Company | Actual production website and its company |
| Service User | Dedicated internal user with **WhatsApp Authentication Worker**, limited to that company |
| Sender | `965292690006920`, if retaining the current WhatsApp sender |
| English template / language | `abdin_authentication_en` / `en_US` |
| Arabic template / language | `abdin_authentication_ar` / `ar` |
| Source | Copy the UUID generated by this production transport |
| Enabled | Enable only when the matching worker configuration and receiver are ready |

The addon provides service user XML ID `ab_storefront_whatsapp_auth.user_auth_worker`. Ensure its company and the transport's assigned user match the production website. Generate a native Odoo API key for this dedicated user on the **production storefront database**. Enter that key only in the private Callcenter auth configuration. Use a bounded lifetime and record its rotation date.

This worker key differs from the Callcenter messaging-service key, Website order-exchange keys, Meta access token and Meta app secret. The production source UUID identifies a transport; it is not an authentication secret.

The Callcenter auth worker must be able to POST over HTTPS to:

- `/ab_storefront/auth/exchange/v1/lease`
- `/ab_storefront/auth/exchange/v1/dispatch`
- `/ab_storefront/auth/exchange/v1/report`
- `/ab_storefront/auth/exchange/v1/status`

It sends `Authorization: Bearer <PRODUCTION_STOREFRONT_WORKER_API_KEY>`, `X-Odoo-Database: <PRODUCTION_STORE_DATABASE>` and the exact production transport Source in each JSON request. The receiving addon checks that source, service user and website company before accessing a challenge.

## 3. Callcenter host: production WhatsApp source

Use [the production auth JSON example](examples/storefront-auth-production.example.json). Replace its example UUID dictionary key, database and API-key placeholders using the production transport above. The configured sender and template languages must exactly match that transport. The provided sender ID and template names are the current local mappings; change them on both sides if production uses different resources.

The example starts disabled. When extending the existing active setup, **merge the production source entry into the existing `sources` mapping** rather than replacing the entire private file. Retain the local source while it has outstanding jobs or delayed receipts. Its UUID must continue identifying the local transport; the new production UUID identifies the production transport.

```ini
Environment=CRM_AUTH_CONFIG=/home/abdin_04/.config/crm-messaging/auth.json
```

```json
  "graph_version": "v26.0",
  "enabled": true,
  "reception": "webhook",
```

These are fields of the existing account entry, not a complete replacement config. Retain its protected Meta access token, Meta app secret (`webhook_secret`), verification token and dedicated Callcenter Odoo key. The auth worker also requires top-level `sending_enabled=true` in the messaging configuration and `enabled=true` in auth configuration; the storefront transport must be enabled too. Account for other existing workers before changing shared sending gates.

Run the authentication-aware receiver factory `app.auth_receiver:create_app` with `--factory`, preserving the existing receiver's other launch parameters and environment. This routes OTP delivery receipts into separate authentication queues. It must load the same `CRM_AUTH_CONFIG` and WhatsApp account mapping as the worker. Run the separate worker using `python -m app.auth_worker`; the installed local user unit is `crm-storefront-auth.service`. Restart/reload the managed receiver as well as the auth worker after adding/changing source mappings so both hold the same configuration. Do not start a second receiver or replace unrelated scoped workers.

Meta's public callback remains:


The user confirmed `hook.abdinpharmacies.com` points to FastAPI on the Callcenter host. ## 4. Production storefront: Telegram authentication

Configure these parameters on the production storefront database:

| Parameter | Value |
| --- | --- |
| `ab_storefront_auth.telegram_enabled` | `True` |
| `ab_storefront_auth.telegram_bot_username` | `Abdin_Pharmacy_Bot`, if retaining that authentication bot; no leading `@` |
| `ab_storefront_auth.telegram_bot_token` | Matching BotFather token, entered privately in administrator System Parameters |
| `ab_storefront_auth.telegram_webhook_url` | `https://store.abdinpharmacies.com/ab_storefront/auth/telegram/webhook` |

Provision a separate random Telegram webhook secret using the shipped `ab_ecommerce_storefront/tools/provision_auth_secrets.py` helper as the storefront service user. It refuses to overwrite an existing secret. Store the directory as 0700 and the secret file as 0600. Supply the file through either:

```ini
ab_storefront_telegram_webhook_secret_file = /absolute/private/path/telegram_webhook_secret
```

or the Odoo service environment:

```ini
AB_STOREFRONT_TELEGRAM_WEBHOOK_SECRET_FILE=/absolute/private/path/telegram_webhook_secret
```

The webhook secret is separate from the BotFather token. Once the matching token, username, HTTPS URL and secret are configured, run the existing private configuration method from an administrator Odoo shell on the **production storefront**:

```python
env['ab_storefront_auth_telegram'].sudo()._configure_webhook()
env.cr.commit()
```

This contacts Telegram, validates the bot username, registers updates `message` and `callback_query`, supplies the secret header and retains pending updates. Register it only when intentionally activating the production authentication bot. Keep the **Storefront authentication delivery** scheduled action active and production cron capacity at least one; queued Telegram codes/approval responses need that worker.

Do not run the Callcenter polling receiver, a development poller or another webhook consumer for this same authentication bot. The staff chatter bot retains its separate Callcenter configuration and consumer. The current implementation uses bot deep links/contact sharing, not Telegram's website Login Widget; a BotFather `/setdomain` setting is not what establishes this integration.
