# Next plan: WhatsApp Sales Operations using ab_whatsapp_api

Updated 2026-11-04 after the user selected the newly pulled `ab_whatsapp_api` as the WhatsApp implementation owner. Source inspected at commit `39e35b41` on `callcenter19`. This is a source diagnosis and implementation plan; the addon was not edited, installed, activated, or connected to Meta during this review.

## Ownership decision

- `ab_whatsapp_api` owns WhatsApp contacts, canonical messages, templates, provider configuration, webhook processing and provider sends.
- Reuse its existing technical model names unchanged: `ab.whatsapp.contact`, `ab.whatsapp.message`, `ab.whatsapp.template`, and `ab.whatsapp.service`.
- `ab_crm_sales_workspace` owns central assignment, authenticated agent identity, customer matching and CRM/OMS orders. Its accepted orders still create no invoice, payment, stock movement, or branch submission.
- Add a small `ab_crm_whatsapp_workspace` integration addon with explicit dependencies on the workspace and `ab_whatsapp_api`. It links the two domains and contributes the WhatsApp conversation renderer/actions. Do not enable a second WhatsApp sender through `ab_crm_whatsapp` or the existing generic gateway WhatsApp path.
- Keep Telegram transport unchanged. The new gateway contact-sharing implementation remains Telegram-specific.

## Reusable implementation

| Existing model/API | Planned use |
| --- | --- |
| `ab.whatsapp.contact` | WhatsApp identity and provider display name; relate to CRM customer/conversation after normalized, authorized matching |
| `ab.whatsapp.message` | Canonical WhatsApp message, direction, provider message ID, delivery state, reply/reaction references and retained source evidence |
| `ab.whatsapp.template` | Existing approved-template catalog and parameter metadata; retain administrative template management |
| `ab.whatsapp.service` | Provider configuration and transport helpers; extend its authorization and durable-send boundaries before exposing agent actions |
| Existing Owl dashboard | Reference for message rendering and interaction; keep the standalone admin dashboard and implement the staff workspace integration without replacing shared components |

Provider credentials already come from protected Odoo host configuration (`whatsapp_token`, `whatsapp_phone_number_id`, `whatsapp_verify_token`, `whatsapp_business_account_id`, `whatsapp_api_version`). Reuse this authority; add a protected app-secret setting for signature verification, not another editable credential directory.

## Confirmed findings to fix before staff activation

1. **P1 — Unauthenticated webhook ingestion and elevated public ORM entry point.** `controllers/main.py:31-46` accepts public POST JSON and immediately invokes `sudo().process_webhook_payload`. No raw-body signature verification is present. `models/whatsapp_service.py:1390` is a public method without a caller check, and invokes helpers that create contacts/messages under `sudo()`. An internet caller can forge incoming messages/statuses through the webhook; an authenticated caller can also invoke the public ORM method directly. Verify the signature and configured recipient account before parsing/processing, bound request size, and make internal processing private or explicitly restrict service callers. The GET verification token does not authenticate POST deliveries.
2. **P1 — No company/branch/account isolation for conversation history.** `models/whatsapp_contact.py:8-25` makes `wa_id` globally unique; contact/message models have no company or intake-branch fields. `security/ir.model.access.csv:2-5` grants all access only to System Administrators. Service list methods at `models/whatsapp_service.py:625-667` use unrestricted elevated searches. Ordinary agents currently cannot use the API; granting them administrator access would expose all conversations and configuration. Add module-owned staff/service groups, company/intake scope, scoped sender-account identity and rules on contacts/messages/outbox/history before agent ACLs are introduced. Validate scope before any elevated read/write.
3. **P1 — Duplicate ingestion and uncertain outgoing delivery.** `models/whatsapp_service.py:1390-1473` creates messages on each webhook delivery, and `models/whatsapp_message.py` has no unique provider-event constraint. `api_send_text` at `models/whatsapp_service.py:1086-1142` performs the provider request before storing the local outgoing record. A duplicate webhook creates duplicate history; a timeout or transaction failure after provider acceptance can encourage a duplicate resend. Add durable event identities/fingerprints, concurrent deduplication, approved outgoing intents, expiring leases, explicit sending/uncertain states and reconciliation. Do not automatically retry an uncertain send.
4. **P1 — History can be destroyed or rewritten.** `api_delete_contact` at `models/whatsapp_service.py:772-785` physically unlinks the contact, and `models/whatsapp_message.py:17-21` cascades message deletion. `api_edit_message_local` and `api_delete_message_local` at `models/whatsapp_service.py:1301-1362` replace the retained text or media references. Use archival and append-only correction/redaction evidence for workspace-linked conversations. Preserve original content, actor, time, source IDs and accepted-order evidence. Existing tests explicitly expect cascading deletion; replace that expectation for protected records.
5. **P2 — Missing reply-window and operational localization evidence.** The text-send path has no customer-service-window check, and incoming processing does not retain provider timestamps as an authoritative inbound-time field. Add the window guard from authenticated provider timestamps and route outside-window communications to approved templates with explicit staff authorization. There are no Arabic catalogs or module changelogs in the pulled addon. Add both Arabic catalogs, translated frontend literals, developer metadata and focused runtime/RTL tests. Verify the configured Graph API version against current official Meta documentation before activation.

These findings are from code inspection, not executed exploit tests. Existing tests cover basic messages, status ordering, media/reaction metadata and template behavior; they are not evidence for webhook authenticity, isolation, concurrency or durable delivery.

## Implementation sequence

1. **Read-only deployment inventory.** Confirm the installed addon version, configured sender account and credential-presence booleans without printing secrets; count existing contacts/messages/templates; identify company and central intake branch mappings. Preserve operational store/replica configurations. Do not infer a company from a global WhatsApp contact. Quarantine unresolved legacy scope until explicitly mapped; no development-state SQL or automatic migration hooks.
2. **Harden the owning addon.** Address the five findings above inside `ab_whatsapp_api`, preserving existing XML IDs and dotted model names. Keep administration separate from staff permissions. Introduce durable incoming/outgoing records and an external worker handoff without adding a second credential source, sender, or cron job. Commit the outgoing intent/lease before provider dispatch; retain uncertain outcomes for review.
3. **Add relational integration.** Link the configured WhatsApp account to the existing central CRM intake branch and its replica/default store. Add a unique relation from the CRM message projection to its canonical `ab.whatsapp.message`; synchronization may maintain a display projection but must never send twice. Link contacts through authorized normalized-phone matching; ambiguous matches require agent selection. Preserve per-account identity and company boundaries.
4. **Embed the conversation in Sales Operations.** Add contacted WhatsApp conversations to the inbox, selection, unread tracking and employee claim flow. Render the selected WhatsApp stream from the linked canonical messages. Route explicit Send through the approved `ab.whatsapp.service` workflow. Display WhatsApp in `#2BBC37` only when selected, with other contacted channels neutral; never label this online presence. Keep reply targets within the selected provider account/conversation.
5. **Reuse CRM/OMS order actions.** Create orders only on explicit agent action. Carry the WhatsApp source and originating conversation into order history. Reuse Draft/Accepted/Closed/Cancelled states, confirmation evidence, price-change audit and revision snapshots. No invoice/POS/`ab_sales` submission.
6. **Verify before activation.** Test ordinary agent/manager/service/public actors, company and branch isolation, forged direct ORM calls, signed/tampered/replayed webhooks, concurrent duplicates, out-of-order statuses, returned identities, ambiguous phones, window expiry, invalid template parameters, lease expiry and ambiguous sends. Assert that order acceptance leaves sales/OMS submission/payment/stock counts unchanged. Run fresh install and targeted upgrade on isolated databases and browser tests in English and both Arabic contexts.
7. **Explicit live pilot approval.** Once protected configuration, HTTPS routing, sender verification, mapped scope and rollback steps are reviewable, request activation authorization. Then receive a real WhatsApp message, match the phone, claim, reply explicitly, prepare/accept an order, and verify retained source/history without sales submission. Never route the same sender through both transports.

## Boundaries and acceptance criteria

Initial WhatsApp integration is text-first, with approved templates only when needed for the permitted reply flow. Reactions, attachments, media downloads, local editing, AI extraction, payments and fulfillment remain separately scoped even though the pulled addon already contains some related methods. Their presence does not automatically authorize exposing them to callcenter staff.

Success means a permitted callcenter employee can operate a WhatsApp conversation and accept a retained CRM/OMS order entirely from Sales Operations, using `ab_whatsapp_api` as the WhatsApp authority, with no cross-company disclosure, duplicate dispatch, erased history or sales submission.
