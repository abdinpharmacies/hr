# Abdin Inventory Audit

Version `19.0.1.0.0` for Odoo 19. Central-server inventory counting, discrepancy review, inventory adjustment and mandatory accounting for one branch per audit. The module uses the existing Abdin inventory, source, unit, tax and journal services.

## Setup

Install `ab_inventory_audit` and its manifest dependencies. The Python environment needs `openpyxl` and `xlsxwriter`; PDF rendering uses the existing Odoo PDF renderer. Sales, Purchase, Cashier, external connectors and replication are not audit dependencies. No demo data, migration, cron or installation hook is provided.

Assign each operator the required companies and `inventory_store_ids` branches. Audit Counter records assigned counts; Audit Read-only Reviewer reads branch reports; Audit Financial Reader additionally sees costs and financial results; Audit Manager prepares, assigns, reviews, approves and posts. Audit membership does not grant general inventory or accounting posting permission. System administrators have the audit administration roles.

An Audit Financial Configuration Administrator also needs accounting authorization to configure the branch. Create effective-dated mappings for inventory, shortage and surplus accounts, document type and any required cost center. The posting actor must independently have the existing accounting account and document-type permissions. Inventory is the journal header account. A configuration already used by a posted audit is preserved; create a later configuration version instead of editing it.

## Operation

1. Create an Audit Session under Inventory → Inventory Audits. Select one branch, full or partial scope, a manager and counters. Partial selections can be populated by category through Workflow while still in Draft. Prepare and Open freezes the selection and creates groups by product, expiry/no-expiry and selling price normalized to the reference unit. Full audits include zero-balance sources with branch movement history. Every opening selected product has a protected coverage record, including products with no ledger history. The selected-product list stays frozen. Products without groups require Start Physical Absence Count and independent manager review of an explicit zero, or a manager-approved stock observation followed by counting.
2. Assign groups through Review / Assign. Use the normal group screen, My Count Assignments or Fast Count. Fast Count shows up to 200 groups; scan a barcode to narrow the selection. Scanning selects a product and never increases a count. Posted stock, pending outgoing reservations and available stock are separate values. Expired stock remains countable and is marked separately.
3. Start Count immediately before physical counting, then confirm quantities. Fractional packs are accepted only when their configured conversions produce a reference-unit quantity. Zero is a count; a group without a confirmed attempt remains uncounted. Only one attempt can be active per group. Cancel an abandoned attempt or request a recount with a reason; previous attempts remain in history.
4. Excel: Export Count Sheet starts attempts for all eligible assigned groups. Workflow → Export Selected Groups allows a smaller selection. Keep the workbook identifiers and hidden metadata intact. Enter quantities in the three unit columns; blank quantity rows remain unconfirmed. Upload through Import Count Sheet, preview, then confirm. Format-version 2 workbooks are bound to the session, groups, attempts, tokens and each group’s counting revision. Reviewing another group does not invalidate an unchanged sheet. Incremental imports leave blank rows active; identical quantities already confirmed for an attempt are a no-op, while changed quantities require a new attempt. All row identifiers are checked even when quantities are blank. Older workbook formats require reasoned cancellation/recount and a fresh export. Duplicate rows, foreign identifiers, formulas, negative/nonintegral conversions and stale revisions are rejected. Reimporting the same completed workbook is idempotent. Limits are 5 MiB uploaded, 40 MiB expanded and 50,000 rows.
5. Review each valid attempt. A nonzero discrepancy requires a reason. The reference is posted stock at the accepted count boundary. Later receipts or sales change current stock, not the accepted discrepancy. Saved movement identities and source membership are compared at start and confirmation, detecting offsetting movements and older pending movements that become saved. New coverage must be included and counted or explicitly excluded; exclusions reduce reported completeness.
6. Review source allocation and valuation. Whole-unit allocation uses largest remainders with source ID as the tie-breaker. A shortage cannot exceed its source reference quantity. Overrides require a reason and must total the accepted discrepancy. Zero-reference surplus requires explicit source selection. Unidentified Physical Stock preserves the original counter, quantity/unit, expiry and notes as a pending observation. Include Stock Observation or Exclude Stock Observation requires a manager and a reason. Inclusion validates overlap and approves unit/expiry/price grouping before counting; it records additional coverage without changing the opening selection. Approve Surplus Source records the proposed existing source or new-source inputs. New sources are created only when posting succeeds. Missing cost blocks approval; zero cost requires a reason.
7. Enter Review and approve the current revision. An authorized manager who performed any accepted count cannot approve or post that audit. Costs, tax inputs, conversion basis and accounting configuration are frozen at approval. Required, active and permitted cost centers are validated through the accounting line validator without creating journals. Changed valuation/configuration requires review and reapproval. A shortage blocked by current stock or reservations retains its accepted count and discrepancy, records affected sources and approved/posted/reserved/available quantities, and marks its allocation unresolved. Use reasoned allocation overrides if needed, then Resolve Blocked Allocation. Resolution and reapproval both check current stock; the accepted discrepancy total and source limits remain mandatory.
8. Post Approved Audit displays the financial totals before confirmation. Posting creates one persistent adjustment per affected source and invokes `inventory_write()` with a positive quantity and its direction. Surplus and shortage journals are balanced separately through `post_journal()` as the actor. Source creation, movements, journals and history share one transaction. A repeated successful posting returns the existing result. Zero discrepancies produce no movement; zero-value totals produce no journal.

Cancel only before posting; archive posted or cancelled audits. Correct a posted result through a new audit linked by Correction Of. Audit-linked journals, movements, adjustment history and posted evidence are preserved. Public/token sharing of audit attachments is prohibited. Add evidence with the chatter attachment button and review it in Attachments.

## Reports and implementation

The session includes product coverage, observations, unresolved allocations, groups, team, attempts, movements after accepted counts, adjustments, approval/accounting, attachments and history. Print menus provide a PDF reference count sheet and PDF/XLSX results, coverage, attempts, source allocation, valuation, later movements, posting reconciliation and journal references. The reference PDF does not start a counting window: start a count or export Excel first. Results identify groups, attempts and the accepted attempt explicitly. Historical movement associations use stored count boundaries and source/allocation links, including late receipts and newly posted surplus sources. Financial sections follow field and record permissions. English source strings have complete `ar.po` and `ar_001.po` catalogs.

| Persistent model | Responsibility |
| --- | --- |
| `ab_inventory_audit` | Scope, team, workflow, approval and posting |
| `ab_inventory_audit_coverage` | Frozen opening/additional product coverage, decisions and completeness |
| `ab_inventory_audit_observation` | Original discovered-stock evidence and manager decisions |
| `ab_inventory_audit_line` | Product/expiry/price count group and accepted discrepancy |
| `ab_inventory_audit_source` | Source references, allocations and frozen valuation |
| `ab_inventory_audit_count` | Immutable attempts and movement boundaries |
| `ab_inventory_audit_adjustment` | One source adjustment and inventory movement identity |
| `ab_inventory_audit_config` | Effective branch accounting mappings |
| `ab_inventory_audit_event` | Actor, time, reason and revision history |

A transient workflow wizard covers count confirmation, assignments, review, recounting, coverage, source proposals, Excel and posting. Inherited protections are owned by this module. The frontend action is scoped to `ab_inventory_audit`; shared POS components are untouched.

## Validation and operating boundary

See [VALIDATION.md](VALIDATION.md) for actual test evidence and measured lock durations. Test scripts and generated evidence are distributed separately from the production addon.

Only movements already available in the central ledger can be monitored. This module cannot establish complete branch delivery or propagate adjustments to independent branch databases. Synchronization and production cutover are outside this implementation. Before any separately authorized pilot, back up and reconcile central inventory, accounting and operational branch balances.

Physical counting holds no persistent branch lock. Preparation, confirmation, approval and posting use transactional locks. A final local stress test posting 1,001 nonzero source adjustments held the branch lock for 54.63 seconds; large adjustment batches need an operational window and capacity validation before live use. Accounting uses the existing source model's tax-inclusive computed cost, rounded at the existing two-decimal journal precision; it does not create separate tax or supplier-liability entries.

The current implementation is for clean development installations and separately validated upgrades. It does not migrate deployed active sessions or reconstruct historical coverage. Workbook version 1 is intentionally incompatible. See [REQUIREMENTS.md](REQUIREMENTS.md) for the acceptance checklist.
