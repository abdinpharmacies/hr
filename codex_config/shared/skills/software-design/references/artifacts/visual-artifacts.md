# Visual work artifacts

Use this route when the user wants a designed report, training guide, handout, presentation, infographic, PDF or similar personal or work artifact. It coordinates the design across formats; use the software routes only if the subject also requires software analysis.

## Decide the artifact

1. Identify the reader, what they must understand or do, the source material, requested format, language and privacy boundary. For a training guide, explain the screen from the reader's point of view: where to go, what each control means, what choosing it permits, examples, and how to check the result. Distinguish navigation labels from permissions or actions.
2. Inventory every named section, field, visible value and relevant available choice in the supplied screen or text before drafting. Reconcile the outline against that inventory before delivery; if part of a long screen is unseen, say which part lacks evidence instead of silently omitting it. Inspect user-provided screenshots and existing reference files. Read the relevant source or official documentation when exact behavior matters. Separate verified facts, inferences, and items that require live verification; do not promise exact effective permissions from a screenshot alone. Do not include private details from a sample account unless they are needed for the requested example.
3. Choose the visual system for the audience and content. For an Arabic operational report or training PDF, use [the Arabic report reference](../../assets/arabic-report-reference.html) as the default visual starting point: A4 pages, right-to-left text, dark blue headings and table headers, teal accents, readable Arabic type, restrained callouts, and a screenshot only when it adds evidence. This reference is based on the Odoo permissions guide and contains generic sample content; replace the sample with the current task and adapt density and page breaks. The user need not restate this design preference. Inspect a user-named template before using it; retain its visual system when it fits. If it does not fit the format, reading direction or information density, use a coherent alternative. Combine template guidance with interface/design guidance only where they complement each other. Do not force an unrelated cover image or an English left-to-right layout onto an Arabic operating guide.
4. Structure the content before styling. Start with a specific title and a short purpose. Use headings, short paragraphs, steps, examples and tables for comparisons or field mappings. Keep each page scannable, use readable type and contrast, and avoid dense full-page tables where a split improves comprehension. A supplied screenshot is evidence and context; a readable explanation must stand on its own.

## Produce and verify

- Use the relevant format skill when available (for example, PDF or documents) and follow its artifact requirements. Use UI/UX guidance for typography, hierarchy, spacing and contrast when it improves the document. For presentations, images, sites and other formats, use their focused skill when available and retain this route for audience, evidence, visual choices and review. This route does not install or require those specialist skills.
- For Arabic and other right-to-left languages, set document direction and fonts that render and shape the script correctly. Check mixed Arabic, English, numbers and code identifiers in the exported file.
- Render the final artifact to page or frame images and inspect every page or frame. Check titles, table headers, screenshot legibility, page breaks, empty spill pages, clipping, font glyphs, RTL order, margins, headers and footers. Extract text or inspect metadata as a second check; extraction alone cannot prove visual quality. Repair the source and render again.
- Deliver the requested final format at a stable path. For presentations, inspect every slide; for infographics and other single images, inspect the complete output at its intended size. Explain what it covers and any material limit on the evidence. Do not present an untested source file as a completed PDF or add unrelated intermediate files to the delivery.

For a permissions guide like the Odoo example, an effective outline is: page orientation and controls, a row-by-row explanation, the combined effect of roles, a worked account example, role-based setup recipes, common misunderstandings, verification steps, and sources. Do not turn this outline into a fixed template for unrelated documents.
