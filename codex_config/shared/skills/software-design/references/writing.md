# Explain and review technical prose

Lead with the answer or recommended decision. Describe responsibilities and interactions in terms the intended reader understands. Connect a change to its reason, benefit and cost. Expand unfamiliar abbreviations on first use, preserve exact identifiers, and use the user's language.

Keep current behavior, evidence, assumptions and proposals distinguishable. Do not turn an inferred reason into a historical fact or a plausible optimization into a measured result. Explain relevant failure paths and limits without burying the answer in a generic checklist.

Use a table for genuinely parallel alternatives and numbered steps for execution order. Diagrams complement prose: explain the important path and what the reader should learn from it. Avoid a file inventory masquerading as an explanation, decorative jargon, repeated summaries and unsupported adjectives.

For a prose review, report concrete passages, why they confuse the reader and the smallest correction, with file/line where available. Preserve technical meaning and project voice. Do not impose Vercel metadata, MDX components or English sentence-length rules on unrelated documentation. Load [Writing audit](writing-audit.md) only for an explicit handbook compliance request.
